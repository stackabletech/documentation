== Release 26.11

=== 26.11.0

Released on 2026-11-20.

[TIP,caption=Release highlights]
====
* OpenLineage support for selected operators and their products
* Resource info fetcher for Open Policy Agent
* Improved KRaft support in the Stackable operator for Apache Kafka

* The Stackable operator for Trino now supports Apache Iceberg REST catalogs

==== New platform features

===== General

====== Resource info fetcher for Open Policy Agent

This release adds an initial version of resource-info-fetcher, which is similar to user-info-fetcher, but allows additional metadata about resource information to be fetched from a data catalog.
DataHub is the only supported data source.

Also, a Rego rule library has been added to make it easier to call resource-info-fetcher from within OPA.
The API, especially the response, is subject to change when support for more data catalogs is added.

Implemented in https://github.com/stackabletech/opa-operator/pull/863[opa-operator#863].

====== OpenLineage

https://openlineage.io/[OpenLineage] is an open standard for collecting data lineage: which jobs ran, which datasets they read, and which datasets they wrote.
Products emit OpenLineage events while they work and send them to an OpenLineage-compatible backend, such as https://marquezproject.ai/[Marquez] or https://docs.datahub.com/docs/lineage/openlineage[DataHub].
The backend stitches the events from all producers into one lineage graph, so you can answer questions such as "where does this table come from?" or "what breaks if I change this column?".
This release adds a unified way to manage OpenLineage configurations across products.
The Stackable operators for link:#airflow-openlineage-26_11_0[Apache Airflow], link:#spark-openlineage-26_11_0[Apache Spark] and link:#trino-openlineage-26_11_0[Trino] provide support for HTTPS backends including authentication.

[#kafka-new-features-26_11_0]
===== Apache Kafka

Operator support for KRaft has been almost completely rewritten in this release, and KRaft is no longer marked as experimental.
KRaft based installations are now much more robust and secure.
Controller scaling is now much more reliable and has almost no impact on broker activity.
Security wise, controllers use the same internal security mechanisms as the brokers regardless of the client facing protocols.
Administrative operations are now subject to the same authorization policies as topic and data management operations.

* *Dynamic KRaft controller scaling:*
  KRaft deployments now support dynamic controller scaling.
  Previously, scaling controllers required manual intervention to update the voter list.
  The voter list is now updated dynamically using a sidecar container and a `preStop` container hook.
  Controllers are scaled one at a time, because KRaft only processes one voter change at a time.
+
--
[.breaking-keyword]**Breaking**
The `podManagementPolicy` of the controller StatefulSet changed from `Parallel` to `OrderedReady`.
This is an immutable field, so the controller StatefulSets must be deleted once after the operator upgrade, see link:#label-improvements-26_11_0[StatefulSets that must be recreated].

Within a controller role group, the recreated StatefulSet restarts the Pods one after another.
The Pods of different controller role groups restart at the same time, so with several controller role groups the KRaft quorum may be unavailable for a few seconds.

Implemented in https://github.com/stackabletech/kafka-operator/pull/1010[kafka-operator#1010].
--

* [#kafka-opa-controllers-26_11_0.breaking-keyword]**Breaking**
  **OPA authorizer for Apache Kafka 4.x:**
  Apache Kafka 4.x now supports the OPA authorizer.
  In KRaft clusters, the controllers now run the OPA authorizer as well, and `super.users` is not set.
+
--
This affects every KRaft cluster that uses OPA authorization (`spec.clusterConfig.authorization.opa`).
OPA now authorizes all requests on the `CONTROLLER` listener: the Raft traffic between the controllers, the registrations and heartbeats of the brokers, and the admin requests that brokers forward to the controllers, such as CreateTopics and DeleteTopics, with the principal of the client.
Forwarded admin requests were not authorized at all before this release.

A policy that treats only the `INTERNAL` listener as internal and only allows the broker certificates, like the example policy of SDP 26.7, denies this traffic.
The controllers are then expected to lose their quorum and the brokers to be fenced, so the whole Kafka cluster stops working.

Before upgrading the operator, extend the Rego policy:

* Treat the `CONTROLLER` listener as internal and allow the certificate subjects of the controllers.
* Allow the admin operations, such as creating topics, for the clients that need them.
  Forwarded client requests arrive on the `CONTROLLER` listener, so client rules must not exclude it.

The extended policy also works with SDP 26.7, where the controllers do not run the authorizer.
See the xref:kafka:usage-guide/security.adoc[security guide] for an example policy.
After the upgrade, watch the controller logs for authorization denials while the Pods restart.

To list the affected clusters:

[source,console]
----
$ kubectl get kafkaclusters -A -o json | jq -r '.items[] | select(.spec.clusterConfig.authorization.opa != null) | "\(.metadata.namespace)/\(.metadata.name) \(.spec.clusterConfig.metadataManager // "default")"'
----

Tracked in https://github.com/stackabletech/kafka-operator/issues/941[kafka-operator#941], implemented in https://github.com/stackabletech/kafka-operator/pull/1051[kafka-operator#1051] and https://github.com/stackabletech/kafka-operator/pull/1069[kafka-operator#1069].
--

* **Management access:**
  SDP can now manage resources inside an Apache Kafka cluster.
  When `spec.clusterConfig.managementAccess` is enabled on a KafkaCluster, the operator deploys an agent next to the cluster, which authenticates to Kafka with a TLS client certificate that the user provides through a SecretClass or a Secret.
  This is supported for clusters in KRaft mode without Kerberos authentication.
  See the xref:kafka:usage-guide/management-access.adoc[management access] documentation page for more details.
+
Implemented in https://github.com/stackabletech/kafka-operator/pull/1028[kafka-operator#1028].

* **Declarative topic management:**
  Topics can now be managed declaratively with the new KafkaTopic custom resource.
  The agent creates, adopts, changes and optionally deletes the topic in Kafka, and reports changes Kafka cannot apply in the status.
  This requires management access to be enabled on the KafkaCluster.
  See the xref:kafka:usage-guide/topics.adoc[topics] documentation page for more details.
+
Implemented in https://github.com/stackabletech/kafka-operator/pull/1045[kafka-operator#1045] and https://github.com/stackabletech/kafka-operator/pull/1050[kafka-operator#1050].

* [#spark-cleanup-26_11_0.breaking-keyword]**Breaking**
  This release introduces the `cleanup` field for the SparkApplication and SparkApplicationTemplate resources, which defines when the Spark driver Pod is deleted.
  You can set different durations for successful and failed Spark runs.
  Without the field, a finished driver Pod is now kept for 10 minutes after a successful run and for 24 hours after a failed one, instead of being deleted right away.
  To delete driver Pods right away, set both durations to `0s` in your SparkApplications and SparkApplicationTemplates.
  A SparkApplication that sets `spark.kubernetes.driver.pod.name` together with a non-zero `cleanup` is rejected.
+
--
[source,yaml]
----
spec:
  cleanup:
    afterSucceeded: 10m
    afterFailed: 1d
----

===== Apache ZooKeeper

[#zookeeper-new-features-26_11_0.breaking-keyword]**Breaking**
ZooKeeper now enables the auto-purge feature for the data directory cleanup by default.

With the default settings, a cleanup runs every 6 hours and keeps only the 3 most recent snapshots and their transaction logs.
Older snapshots and transaction logs are deleted.
This mitigates the data directory filling up the PersistentVolume.

If you back up or read old snapshots or transaction logs from the data directory, turn auto-purge off before upgrading the operator:

[source,yaml]
----
spec:
  servers:
    configOverrides:
      zoo.cfg:
        autopurge.purgeInterval: "0"
----

For more on the process, check the xref:zookeeper:data_directory.adoc#_snapshot_creation_and_auto_purge[documentation page] and xref:zookeeper:reference/zoo_cfg_properties.adoc#data-dir-props[the reference] for the defaults.

===== Open Policy Agent

OpaClusters can now be deployed as a Deployment instead of a DaemonSet, selected with `spec.servers.roleConfig.workloadKind`.
The default stays `DaemonSet`.
A Deployment gets a PodDisruptionBudget, configurable with `spec.servers.roleConfig.podDisruptionBudget`, and default affinities that distribute the Pods evenly across the nodes where possible.

===== Trino

* [#trino-openlineage-26_11_0]#This release adds OpenLineage support for Trino#
+
--
The operator can now configure Trino clusters to emit https://openlineage.io/[OpenLineage] lineage events to a backend such as Marquez or DataHub.
You can enable it with the new `spec.clusterConfig.lineage` field of the TrinoCluster custom resource.

Implemented in https://github.com/stackabletech/trino-operator/pull/914[trino-operator#914].
--

* The Iceberg connector can now connect to an https://trino.io/docs/current/object-storage/metastores.html#rest-catalog[Apache Iceberg REST catalog] via the new `spec.connector.iceberg.catalog.rest` field of the TrinoCatalog.
  Trino can optionally authenticate against the REST catalog using OAuth2, with either client credentials or a static Bearer token read from a Secret.
  Connections don't use TLS by default, but webPki or custom CA certificates can be specified.
  Previously, a REST catalog could only be configured using `configOverrides`.
+
--
For this, TrinoCatalog version `v1alpha2` was added and is now the stored version.
It replaces the optional `spec.connector.iceberg.metastore` field with the required `spec.connector.iceberg.catalog` field, which is one of `rest`, `hiveMetastore` or `userProvided`.

TrinoCatalogs can still be applied and retrieved in `v1alpha1`, and conversion between both versions is handled automatically by default.
A `v1alpha1` `metastore` becomes `catalog.hiveMetastore`, and a missing `metastore` becomes `catalog.userProvided`, so TrinoCatalogs that configure a REST catalog via `configOverrides` keep working unchanged.
A `rest` catalog can't be represented in `v1alpha1`, so use `v1alpha2` for all TrinoCatalogs that use one.

[#trino-catalog-conversion-26_11_0.breaking-keyword]**Breaking**
The conversion runs in a conversion webhook of the operator, which is only set up when the operator maintains its CRDs.
If you set `maintenance.customResourceDefinitions.maintain: false` in the Helm values, only `v1alpha2` TrinoCatalogs can be used, and TrinoCatalogs stored as `v1alpha1` are not converted.
Rewrite every TrinoCatalog as `v1alpha2` before upgrading the operator.
To check whether the operator maintains its CRDs:

[source,console]
----
$ helm get values trino-operator -n <namespace> -a | grep -A2 customResourceDefinitions
----

See the xref:trino:usage-guide/catalogs/iceberg.adoc[Iceberg connector documentation] for details.

Implemented in https://github.com/stackabletech/trino-operator/pull/950[trino-operator#950].

====== Miscellaneous

* The labels attached to the Kubernetes objects created by the operators have been reworked so that only the recommended labels that apply are present.
  The `app.kubernetes.io/component` and `app.kubernetes.io/role-group` labels are no longer set on objects that do not belong to a single role or role group (previously they were set to `none` or a placeholder value).
  For most operators, this needs no action.
+
--
[#label-improvements-26_11_0.breaking-keyword]**Breaking**
The following StatefulSets cannot be updated in place and must be deleted once, right after the operator upgrade, so that the operator immediately recreates them:

* **Apache HBase:** The REST server StatefulSet of every REST server role group because the `app.kubernetes.io/managed-by` value on the claim template changes.
* **Apache Spark:** The history server and Spark Connect server StatefulSets.
  The Spark Connect server additionally loses the placeholder `app.kubernetes.io/role-group: default` from its selector.
  The orphaned Pods still match the new selector and are adopted.
* **OpenSearch:** The nodes StatefulSet of every role group.
  Also consult the xref:opensearch:usage-guide/upgrade.adoc#_upgrade_from_sdp_26_7_to_26_11[OpenSearch upgrade guide] for further details.
* **Apache Kafka:** The KRaft controller StatefulSet of every controller role group because it changes its `podManagementPolicy` from `Parallel` to `OrderedReady`.

Up to SDP 26.7, the operators set the `app.kubernetes.io/version` label on the volume claim templates of the HBase, Spark and OpenSearch StatefulSets to the product version, which changes with every upgrade.
These operators no longer set this label there, so this is the last upgrade that requires deleting these StatefulSets.

Use `--cascade=orphan` to retain the Pods:

[source,console]
----
$ kubectl delete statefulsets.apps --cascade=orphan <statefulset-name>
----

The recreated StatefulSet adopts the orphaned Pods and restarts them one after another to apply the new product image.

**Do not skip this.** The cluster keeps running and stays healthy, so the error is easy to overlook, but the operator cannot apply any further change to the affected StatefulSets, including the number of replicas and the product version, until they are deleted.
The reconciliation error looks like this:

[source,plain]
----
... is invalid: spec: Forbidden: updates to statefulset spec
for fields other than 'replicas', ...
----

On SDP 26.7, changing the product version of the HBase, Spark and OpenSearch StatefulSets, as the upgrade guide describes for versions that SDP 26.11 no longer supports, fails with the same error.
Delete them the same way after changing the version.

Tracked in https://github.com/stackabletech/issues/issues/877[issues#877].
--

* [#run-as-non-root-26_11_0.breaking-keyword]**Breaking**
  All product Pods now run with `securityContext.runAsNonRoot: true`.
  The operators set no `runAsUser`, so Kubernetes takes the user from the image and refuses to start a container whose image runs as root, or names its user instead of giving a numeric ID.
  The Pod then fails with `CreateContainerConfigError`.
  The Stackable images run as a numeric non-root user and are not affected.
+
--
You are affected if you use one of the following:

* a custom product image (`spec.image.custom`) whose last `USER` is root, unset or a name such as `stackable`, for example because it switches to `USER root` to install packages and back to `USER stackable`
* a Spark job image (`spec.image` of a SparkApplication) that runs as root, because it runs as the `job` init container of the driver Pod
* `podOverrides` that set `runAsUser: 0`

Before upgrading the operators, check each of these images.
The result must be a number other than `0`:

[source,console]
----
$ docker inspect -f '{{.Config.User}}' <image>
----

Fix the image by using a UID, such as `USER 1000`, or set `spec.securityContext.runAsUser: 1000` in the `podOverrides`.
If an image really has to run as root, restore the behaviour of earlier releases with `podOverrides`:

[source,yaml]
----
podOverrides:
  spec:
    securityContext:
      runAsNonRoot: false
----

For a SparkApplication, set the override on the driver, because the job image runs in the driver Pod, and on the executor and the submit Job if their images are affected.

Implemented in https://github.com/stackabletech/operator-rs/pull/1205[operator-rs#1205].
--

* [#env-overrides-26_11_0.breaking-keyword]**Breaking**
  An `envOverrides` entry for an environment variable that the operator also sets now replaces the operator's value.
  Before this release, the operator's value won, so such overrides had no effect.
  Before upgrading the operators, review your `envOverrides`: overrides that did nothing so far take effect now.

* Without `spec.image.pullPolicy`, the image pull policy is now `IfNotPresent` for images with a fixed tag.
  It stays `Always` for floating tags, such as custom images tagged `latest` or without a tag, and for `stackableVersionPolicy: LatestPatch`.
  A custom image that is pushed again under the same tag is no longer pulled again on nodes that already have it.
  Set `spec.image.pullPolicy: Always` for such images, or use immutable tags.

* [#vector-26_11_0.breaking-keyword]**Breaking**
  The Vector agent in the product Pods is now Vector 0.58.
  The `ADDRESS` in the aggregator discovery ConfigMap must be a URL with a scheme, such as `http://vector-aggregator.vector.svc.cluster.local:6000`, and the aggregator must run Vector 0.58.
  Otherwise, the logs of all stacklets no longer reach the aggregator.
  Update the ConfigMap and the aggregator together with the operator upgrade.

===== Open Policy Agent

* [.breaking-keyword]**Breaking**
  The `userinfo` and `resourceinfo` Rego rule libraries now only return a value when the fetcher responds with `200 OK`, and pass an explicit 5 second timeout.
  Previously the body of an error response was returned to the policy as if it were user/resource information.
  A rule that defaulted a missing field (eg: `object.get(user, "groups", [])` and the like) would have read a failed lookup as "this user is in no groups" and could have allowed what it should have denied.

Implemented in https://github.com/stackabletech/opa-operator/pull/863[opa-operator#863].

Previously, the HDFS operator configured the AES cipher for HDFS block data transfer under a misspelt key that Hadoop ignored, so with Kerberos enabled, block data was protected only by SASL DIGEST-MD5 encryption, not AES/CTR.

==== Upgrade from 26.7

====

===== Using stackablectl

====== Upgrade with a single command

Starting with stackablectl Release 1.0.0 the multiple consecutive commands described below can be shortened to just one command, which executes exactly those steps on its own.

[source,console]
----
$ stackablectl release upgrade 26.11
----

====== Upgrade with multiple consecutive commands

Uninstall the `26.7` release

[source,console]
----
$ stackablectl release uninstall 26.7

Uninstalled release '26.7'

Use "stackablectl release list" to list available releases.
# ...
----

The operators maintain their own CustomResourceDefinitions (CRDs) and update them automatically on startup, so no manual CRD upgrade step is required.
See xref:concepts:maintenance/crds.adoc[] for details.

Install the `26.11` release

[source,console]
----
$ stackablectl release install 26.11

Installed release '26.11'

Use "stackablectl operator installed" to list installed operators.
----

===== Using Helm

Use `helm list` to list the currently installed operators.

You can use the following command to uninstall all operators that are part of the `26.7` release:

[source,console]
----
$ helm uninstall airflow-operator <PRODUCT>-operator ...
release "airflow-operator" uninstalled
release "<PRODUCT>-operator" uninstalled
...
----

The operators maintain their own CustomResourceDefinitions (CRDs) and update them automatically on startup, so no manual CRD upgrade step is required.
See xref:concepts:maintenance/crds.adoc[] for details.
